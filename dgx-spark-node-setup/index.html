DGX Spark · GB10 · 초기 셋업

DGX Spark 한 대를 추론 서버로 길들이기 — 세 번째 노드 초기 셋업 기록

관련 글: GB10 전력 상한 거는 법 → · LLM 추론에서 가장 뜨거운 것은 GPU가 아니었다 →

GB10 머신(ASUS Ascent GX10, DGX Spark 제품군)을 한 대 더 들였다. 앞의 두 대는 몇 주에 걸쳐 손을 봐 온 상태라, 이번 목표는 단순했다 — 공장 상태의 새 기계를 기존 두 대와 똑같은 추론 서버 베이스라인으로 만드는 것. 그 과정을 재현 가능한 절차로 남긴다. 모델을 올려 돌린 실험과 우리 집 네트워크에만 해당하는 설정(VLAN·주소·스위치)은 빼고, 어느 GB10 머신에나 적용되는 작업만 적는다.

무엇을 바꾸나. 데스크탑 이미지를 서버 모드로(플랫폼 패키지를 지키면서), 드라이버 580 → 595, GPU 클럭 상한 2000MHz + CPU 성능코어 상한 2.8GHz, USB-C PD 펌웨어 최신화, 키 전용 SSH·방화벽·보안 업데이트 자동화. 한 번 재부팅으로 끝난다.

왜 그대로 못 쓰나. 공장 이미지는 GNOME·snap 13개가 올라간 데스크탑이고(UMA 메모리를 수 GiB 먹는다), 드라이버 580.173에는 우리가 재현한 결함이 있고, PD 펌웨어는 초기 리비전이라 "저클럭 고착" 버그에 노출돼 있으며, 보안 업데이트 자동화는 꺼져 있다. 그리고 기본 설정에서는 추론 중 GPU보다 CPU가 먼저 뜨거워진다.

한 가지 안심되는 점: 부팅 파라미터(initcall_blacklist=tegra234_cbb_init, pci=pcie_bus_safe, iommu.passthrough=0)와 /etc/default/grub.d/의 NVIDIA 스니펫 10개는 기존 노드와 동일했다. 이것들은 뒤에서 "지켜야 할 것"으로 다시 등장한다.

1. 서버 모드 전환 — 플랫폼 패키지를 지키면서

데스크탑을 걷어내는 일 자체는 apt purge 몇 줄이다. 문제는 그 뒤의 apt autoremove --purge다. 두 번째 노드를 셋업할 때 이 명령이 NVIDIA 플랫폼 패키지 14개를 통째로 걷어간 적이 있다. 이 패키지들은 dgx-spark-ota-update-meta라는 메타패키지의 의존으로만 잡혀 있어서, 메타가 snapd와 함께 빠지는 순간 "아무도 원하지 않는 패키지"가 된다. 실질 피해는 부팅 파라미터 스니펫 두 개(nvidia-spark-initcall-bl, nvidia-spark-grub-pci)의 유실이었고, 재설치 + update-grub + 재부팅으로 복구했었다.

이번에는 세 겹으로 막았다.

  1. purge 전에 수동 설치 표시. 메타의 Depends(snap 관련 항목 제외)와 기존 노드의 apt-mark showmanual 목록을 합쳐 57개를 apt-mark manual로 박았다. 메타에 새로 추가된 의존 5개(nvidia-spark-avahi-conf, nvidia-spark-limits, nvidia-spark-ota-check, nvidia-enable-bt-profiles, nvidia-desktop-default-remove-gnome-software-deb)는 먼저 개별 설치했다.
  2. 시뮬레이션 게이트. apt-get -s purge …와 apt-get -s autoremove --purge의 Remv 목록에 드라이버·커널 모듈·CUDA·docker·nvidia-spark-*·tailscale이 하나라도 섞이면 스크립트가 중단한다.
  3. 사후 대조. 플랫폼 패키지 9종 dpkg -s, /etc/default/grub.d/ 10개, update-grub 후 grub.cfg의 파라미터 3종을 기존 노드와 비교한다.
# 보호
apt-mark manual $(dpkg -l | awk '/^ii/{print $2}' | grep -E 'nvidia-spark|dgx-spark-mlnx|nvidia-lvfs|nvidia-grub|nvidia-earlycon|nvidia-console|lldpd|nvidia-container|docker-ce|cuda-toolkit-13-0')
# 전환
systemctl set-default multi-user.target
apt-get -s purge ubuntu-desktop ubuntu-desktop-minimal gdm3 gnome-shell xorg xwayland \
  snapd nvidia-system-station dgxstation-desktop dgx-oobe-desktop dgx-spark-ota-update-meta \
  | grep ^Remv | grep -E 'nvidia-driver|linux-modules-nvidia|cuda|docker|nvidia-spark' && echo STOP
apt-get purge -y …same list… && apt-get -s autoremove --purge | grep ^Remv | grep -E 'nvidia-spark|lldpd' && echo STOP
apt-get autoremove --purge -y && rm -rf /snap /var/snap /var/lib/snapd ~/snap
# 대조
grep -o 'initcall_blacklist=[^ ]*\|pci=pcie_bus_safe\|iommu.passthrough=[0-9]' /boot/grub/grub.cfg | sort -u

OTA 메타패키지는 일부러 되살리지 않는다. 복구하면 nvidia-desktop-default-snaps를 통해 snapd가 돌아와 서버 모드가 깨진다. 메타가 하는 일은 "다음 릴리스에서 NVIDIA가 추가하는 패키지를 끌어오는 것"뿐이라, 가끔 apt-cache show dgx-spark-ota-update-meta | grep ^Depends와 설치 상태를 대조해 빠진 것만 개별 설치하면 된다. 개별 플랫폼 패키지는 apt upgrade로 정상 갱신된다.

서버 모드의 보상은 메모리다. GB10은 CPU와 GPU가 128GB LPDDR5x 한 풀을 나눠 쓰는데, 데스크탑 호스트는 유휴 상태에서 약 114.5GiB가 비어 있다고 보고되는 반면(커뮤니티 레시피들이 호스트 RAM 가용치로 인용하는 수치), 서버 모드의 이 노드는 유휴 MemAvailable 119.0GiB였다. 모델을 최대 크기로 올릴 때 그 4~5GiB가 KV 캐시가 된다.

2. 드라이버 580 → 595

교체 이유는 성능이 아니라 결함이다. 580.173.02에서는 디스크 KV 오프로딩 경로에서 Xid 13이 재현됐고, 양 노드를 595.84로 올리자 같은 코드·같은 프로브에서 사라졌다. 그래서 새 노드도 처음부터 595로 맞춘다.

apt-get -s install nvidia-driver-595-open linux-modules-nvidia-595-open-nvidia-hwe-24.04 \
  | grep -E '^(Inst|Remv)' | awk '{print $1}' | sort | uniq -c     # Inst 18 / Remv 16 — 제거는 전부 580 계열이어야 한다
apt-get install -y nvidia-driver-595-open linux-modules-nvidia-595-open-nvidia-hwe-24.04

두 가지만 주의하면 된다. linux-modules-nvidia-595-open-nvidia-hwe-24.04는 실행 중인 커널에 맞는 프리빌트 모듈 패키지(여기선 …-6.17.0-1031-nvidia)를 끌어오므로 DKMS 빌드가 없고, 커널이 다른 노드와 달라도 각자 알아서 맞는다. 그리고 595에서는 nvidia-smi의 일부 쿼리(clocks.applications.*, display_mode)가 "Requested functionality has been deprecated"를 돌려준다 — 점검 스크립트가 이 문자열을 값으로 오해하지 않게 해 둘 것. 롤백은 apt-get install nvidia-driver-580-open=580.173.02-0ubuntu0.24.04.1 linux-modules-nvidia-580-open-nvidia-hwe-24.04로 대칭이다.

3. 클럭 상한 — GPU와 CPU, 이유가 다르다

GPU: -lgc 300,2000

GB10에는 와트 단위 전력 한도(nvidia-smi -pl)가 없다. 유일한 손잡이는 클럭 상한이고, 2000MHz(실스텝 1989)로 묶으면 같은 부하에서 클럭 −17%에 전력 −40%가 나온다(V²f 효과). 배경과 실측은 별도 글에 있다. 새 노드에는 같은 systemd 유닛을 그대로 복사한다.

# /etc/systemd/system/gpu-clock-cap.service
[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/bin/nvidia-smi -lgc 300,2000
ExecStop=/usr/bin/nvidia-smi -rgc
[Install]
WantedBy=multi-user.target

한 가지 짚어 둘 것: 이 상한은 벤치마크 조건이다. 성능 수치를 기록할 때는 클럭 조건을 함께 적어야 하고, 이 노드에서 나온 숫자는 전부 "1989MHz 캡" 조건이다.

CPU: 성능코어 2.8GHz — vLLM이 CPU를 태우기 때문에

CPU 상한은 GPU와 사연이 다르다. 출발은 "LLM 추론 중인데 왜 CPU가 뜨거운가"였다. GB10 2노드에서 vLLM TP=2로 디코드를 돌리면 GPU는 70°C 안팎인데 성능코어 3~4개가 100%에 박혀 SoC 온도를 96°C까지 끌어올렸다. py-spy로 스택을 뜨니 vLLM의 프로세스 간 메시지 큐(shm_broadcast.py)가 새 메시지를 기다리는 동안 busy_loop_s=1 기본값으로 1초씩 스핀하고 있었다 — 매 디코드 스텝마다. 자세한 추적과 한 줄 수정(busy_loop_s 1 → 0.002, CPU 333% → 89%, SoC −11°C, 성능 무손실)은 원 기사와 재현 실험에 있다.

그 수정은 소프트웨어 쪽 해법이라 우리가 돌리는 컨테이너 이미지 안에 핫픽스로 들어가 있다. 하지만 새 이미지, 새 엔진, 새 실험이 올 때마다 스핀이 다시 살아날 수 있다. 그래서 호스트 레벨의 보험으로 성능코어 클럭 상한을 함께 건다. GB10의 20코어는 성능코어 10개(최대 3.9GHz)와 효율코어 10개(2.8GHz)로 나뉘는데, 성능코어를 효율코어와 같은 2.8GHz로 묶는다. 실측으로는 SoC −9°C, 성능코어 −14°C였고, 대화형 단일 스트림에서는 손실이 없었으며 동시성 8에서 −5%였다. 추론은 대부분 메모리 대역폭에 묶여 있어 CPU 클럭을 낮춰도 토큰 속도가 거의 안 바뀌는 반면, 스핀하는 코어의 발열은 클럭에 그대로 비례한다.

# /etc/systemd/system/cpu-clock-cap.service — 성능코어(3.9GHz)만 2.8GHz로
[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/bin/bash -c 'for p in /sys/devices/system/cpu/cpufreq/policy*; do \
  m=$(cat $p/cpuinfo_max_freq); \
  if [ "$m" -gt 2808000 ]; then echo 2808000 > $p/scaling_max_freq; fi; done'
ExecStop=/usr/bin/bash -c 'for p in /sys/devices/system/cpu/cpufreq/policy*; do \
  cat $p/cpuinfo_max_freq > $p/scaling_max_freq; done'
[Install]
WantedBy=multi-user.target

/sys/devices/system/cpu/cpufreq/boost는 이 플랫폼에서 기본값이 0이라 따로 손댈 게 없다. 두 유닛을 enable --now하고 확인하는 한 줄: 성능코어 scaling_max_freq가 2808000, 부하 중 GPU 클럭이 1989MHz, boost 0.

정리하면 — GPU 상한은 전력·발열의 상한이고, CPU 상한은 소프트웨어 스핀이 재발했을 때의 안전망이다. 둘 다 수치가 아니라 이유를 알고 걸어야 나중에 풀 수 있다.

4. USB-C PD 펌웨어

GB10 전 제조사 변종에서 반복 보고되는 버그가 있다. 풀로드인데 클럭이 400~950MHz에 고착되고 성능이 1/3로 떨어지는데, 스로틀 플래그는 전부 Not Active다. 원인은 USB-C PD 컨트롤러 펌웨어의 전원 협상 오인이고, 재부팅으로는 안 풀리며 전원 케이블을 뽑고 방전해야 풀린다. 예방은 PD 펌웨어 최신화인데, 이 노드의 PD 펌웨어는 0x1이었고 LVFS에 0x516(긴급도 High)이 올라와 있었다.

fwupdmgr get-updates            # "GX10 USB-C PD FW Controller Update" 0x516
fwupdmgr update -y --no-reboot-check
ls /boot/efi/EFI/ubuntu/fw/     # fwupd-….cap 이 스테이징되면 재부팅 시 적용 (capsule-on-disk)
# 재부팅 약 2분, 이후 fwupdmgr get-devices 에 0x00000516

재부팅을 한 번만 하려고 드라이버·서버 모드·펌웨어를 같은 사이클에 묶었다. 참고로 같은 경로로 "GX10 SoC FW"(UEFI)와 EC 펌웨어도 내려온다 — ASUS 몫은 펌웨어뿐이고 OS·플랫폼 패키지는 NVIDIA 저장소에서 온다.

6. 밟은 함정

  • 공장 docker의 buildkit DB가 손상본이었다. 재부팅 후 docker.service가 error creating buildkit instance: invalid database로 실패. /var/lib/docker/buildkit(2025-09 생성, 빌드 캐시일 뿐)을 치우고 재시작하면 정상. 이미지·컨테이너와 무관하다.
  • /tmp는 부팅 시 비워진다. 재부팅 전에 스테이징 파일을 홈으로 옮기지 않으면 사라진다.
  • pgrep -f <스크립트명>은 자기 자신을 잡는다. ssh로 원격 실행한 대기 루프의 명령줄에 같은 문자열이 들어 있어 "아직 실행 중"으로 영원히 판정했다. [d]ownload.sh 같은 괄호 패턴이 정답. (pkill -f도 같은 이유로 자살한다.)
  • 595의 deprecated 쿼리. nvidia-smi --query-gpu=clocks.applications.graphics가 문자열을 돌려줘 점검 스크립트의 숫자 비교가 깨진다.
  • 200G ConnectX-7은 케이블이 없으면 lspci에도 안 보인다. 핫플러그 패키지가 관리하는 정상 동작이라 드라이버 문제로 오해하지 말 것 — 케이블을 꽂으면 나타난다.
  • autoremove는 메타패키지 의존을 걷어간다. 위의 세 겹 방어가 그 답이다. 큰 purge 뒤에는 /proc/cmdline을 기준 노드와 대조한다.

부록. "BIOS에서 Display를 끄면 메모리가 는다"는 조언에 대해

단일 노드 레시피 쪽에서 "데스크탑/디스플레이가 UMA 7GiB를 쥐고 있다"는 말이 돌고, 그 연장선에서 "UEFI에 Display 관련 항목이 있으면 끄라"는 조언도 봤다. 확인해 봤다.

  • NVIDIA 공식 DGX Spark UEFI 가이드의 Advanced 탭에는 Display·Graphics·메모리 관련 항목이 없다. fwupdmgr get-bios-settings도 "미지원".
  • ASUS 펌웨어 캡슐(LVFS "GX10 SoC FW")을 풀어 설정 폼(HII/IFR)을 추출해 보면 Advanced → Platform Configuration 폼에 Display(Enable/Disable)·iGPU·iGPU Memory Carveout(기본 24)·Available System Memory(32/64/128) 항목이 실제로 있다. 그러나 전부 SuppressIf TRUE — 화면에 나오지 않는 엔지니어링 숨김 항목이다. 보이는 건 DRAM Encryption·Watchdog Timer·Wireless LAN&BT뿐.
  • 메모리 수지로 보면: 물리 128GiB → 펌웨어 예약 약 3.5GiB(그중 3.0GiB가 carveout 24×128MiB로 추정) → 리눅스 MemTotal 121.6GiB → 서버 모드 유휴 가용 119.0GiB. 커뮤니티가 말한 "7GiB"는 펌웨어가 아니라 GNOME/Xorg의 GPU 할당이고, 서버 모드로 전환하는 순간 돌아온다. 숨김 변수를 efivarfs로 직접 쓰는 건 가능해 보이지만 부팅·GPU 초기화 영향이 미검증이라 하지 않았다.
